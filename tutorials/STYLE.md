# LATW dev-branch tutorial style guide (the authoring contract)

Every notebook on the `dev` branch follows this contract. It exists so
multiple authors (human or agent) produce one coherent workshop.

## The two tiers

- **Informational** (`tutorials/NN_Name.ipynb`, `00`–`08`): purely
  instructive, no exercises. Committed WITH executed outputs (the lisatools
  Sphinx docs import them with `nbsphinx_execute = "never"`).
- **Further / exercises** (`tutorials/further/`): the workshop exercise
  series (Tasks + Questions). The ANSWER notebooks
  (`further/answers/XN_Name-complete.ipynb`) are the source of truth and
  are committed with executed outputs; the student notebooks
  (`further/XN_Name.ipynb`) are GENERATED by `scripts/remove_answers.py` —
  never edit them by hand. Baseline for this tier: *"If you want to do a
  real research project on LISA data analysis, you should generally
  understand and be able to work through these different tutorials."*

## Notebook skeleton

1. **Cell 1** (markdown): H1 title — `# NN: Title` / `# XN: Title`.
2. **Cell 2** (markdown): the environment cell. Dev branch = NO Colab
   support; state that this notebook requires the development stack:
   ```
   git clone https://github.com/lisa-analysis-tools/lisa-analysis-tools.git LISAanalysistools
   bash LISAanalysistools/install.sh
   ```
3. **Cell 3** (code): thread pins FIRST, then standard imports:
   ```python
   import os
   for _v in ("OMP_NUM_THREADS", "OPENBLAS_NUM_THREADS", "MKL_NUM_THREADS",
              "VECLIB_MAXIMUM_THREADS", "NUMEXPR_NUM_THREADS"):
       os.environ.setdefault(_v, "1")

   import numpy as np
   import matplotlib.pyplot as plt
   %matplotlib inline
   from copy import deepcopy
   from lisatools.utils.constants import *
   ```
4. Intro paragraph ("In this tutorial, we will ...") + for informational
   notebooks a **"How to read this notebook"** cell: casual readers read
   the H2 sections and their TL;DRs only; pipeline developers read
   everything including the "Going deeper" subsections.

## Informational-tier conventions

- One topic per **H2** (`##`) section. Every H2 opens with a short
  **TL;DR** markdown cell (2–4 sentences: what this is, when you need it)
  followed by ONE minimal runnable cell showing the essential call.
- Detail goes in `### Going deeper: <topic>` H3 subsections beneath the
  H2 — internals, extra knobs, edge cases, cross-package links.
- Link liberally: Sphinx API docs, the relevant `docs/*.md` developer
  guides, and other tutorials by number ("see 07 §Recipes").

## Further-tier conventions (inherited from LATW main)

- Exercises are **`## Task N: <short title>`** H2 headers. The task body
  is the FOLLOWING markdown cell and ends with a "Useful documentation:"
  bullet list (Sphinx doc links + the relevant informational notebook
  section). Then an import-stub code cell (`# imports` + the key
  `from ... import ...` lines) and the answer cell(s).
- **Answer cells** carry `# clear` as their first line (whole cell blanked
  for students). For fill-in-the-blank, end just the solution lines with
  `# clear-line` (only those lines are removed).
- Discussion prompts are **`### Question`** (or `### Question N`) H3
  cells — conceptual, often no code, aimed at group discussion.
- Say explicitly when a short chain is NOT converged and what a real run
  would need.

## Code rules (sprint conventions apply to tutorial code too)

- Backend choice at construction: `force_backend="cpu"` etc. NEVER
  `use_gpu=` kwargs.
- NO `DataResidualArray` anywhere — it is a deprecated shim; always use
  the `DomainBase` signal classes (`TDSignal`/`FDSignal`/`WDMSignal`/
  `STFTSignal`).
- Do not teach retired/stale modules (see 00's do-not-use list).
- Use installed packages only — no local helper modules in this repo.
- Waveforms via the stock `lisatools.sources` classes (aligned with the
  all_sources defaults) unless the tutorial is specifically about a
  lower-level layer.

## Budgets (checked by `scripts/run_all.sh` at every gate)

- **Runtime**: 00 <1 min; 01 ≤10 min; 02/03/06 ≤5 min; 04/05 ≤8 min;
  07 ≤10 min; 08 ≤20 min; every X answer notebook ≤10 min. Laptop CPU,
  one kernel at a time, all thread env pinned to 1.
- **Memory**: size every example so peak RSS stays at a few GB and the
  laptop stays responsive — short Tobs / small WDM grids / low leaf
  counts / short waveforms. Known trap: full-span MBH phentax generation
  OOMs on a laptop; use a short window.

## Docstring currency rule

When you teach a symbol, read its docstring first. If it is stale
(signature drift, undocumented params, `use_gpu`-era or retired-API
references), fix it in the owning repo in the same work batch — scoped to
symbols the tutorials teach or the stock global-fit pipelines call. Stale
docs on code OUTSIDE that scope: do not fix now; append the symbol to
`tutorials/doc_audit_deferred.md` instead.
